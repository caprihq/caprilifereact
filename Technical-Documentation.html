CAPRI for iOS — Technical Documentation

React Native rewrite of the CAPRI productivity app

Version 3.0.0 (build 25)  ·  iOS 15.1+  ·  Ships as an update to the existing App Store listing — same bundle identifier and same subscription project, so current users and paying subscribers carry over untouched.

1Application architecture

The app was rebuilt from a web page running inside a wrapper into a genuine native iOS application. Screens are drawn by iOS itself rather than by a browser, which is what makes scrolling, typing and animation feel like the rest of the phone.

FrameworkBare React Native 0.86.2 with React 19.2.3. No Expo — every native capability is compiled in directly, so nothing is limited by a third-party runtime.
EngineNew Architecture enabled (Fabric renderer + TurboModules) on the Hermes JavaScript engine. This is Apple-era React Native, not the legacy bridge.
LanguageTypeScript in strict mode throughout. No untyped files, functional code only — no classes.
Server dataTanStack Query v5. One cache, one set of keys, automatic refresh when the app returns to the foreground.
Device dataZustand over MMKV (synchronous storage, so the theme is correct on the first frame). Credentials live in the iOS Keychain, never in MMKV.
NavigationReact Navigation 7 — native stack and bottom tabs, with universal-link and custom-scheme routing.
StylingUnistyles 3 with a design-token system. Five colour moods × light and dark, switchable at runtime with no reload and no hard-coded colours anywhere in the components.
Code layoutVertical feature slices — src/features/<slice>/{screens, components, hooks, logic, services}. Everything under logic/ is pure: no React, no React Native, no network, so it is testable in isolation.
Test suite639 automated tests across 68 suites, plus enforced limits on file and function size, run by a single npm run verify.

3Environment configuration

There is no .env file and no runtime configuration lookup — a deliberate decision. Bare React Native has no equivalent of Expo's config system, so values live as typed constants that the compiler checks and the tests guard.

config/base44.config.tsBackend application id, base URL, and the app's custom URL scheme (capri). None are secret — all three are already public in the shipped web client.
config/constants.tsData-freshness policy: 30-second staleness, 2 retries, 24-hour cache retention.
config/plans.tsWhich features belong to which subscription tier, in one place.
Drift protectionconfigConstants.test.ts fails the build if the bundle identifier or URL scheme in these files stops matching Info.plist and AndroidManifest.xml — a class of bug that is otherwise invisible until sign-in breaks in production.
SecretsNothing secret is compiled into the app. The subscription SDK key is a publishable key by design; the notification signing key exists only on the server.

4Base44 backend integration

All application data lives in Base44. The app talks to it in two ways: typed record access, and named server functions for anything that needs to run privately.

RecordsTyped wrappers for Task, Commitment, User, FocusTime, AIUsageLog and PushDevice. Every query key is generated from one factory, so an update can never miss a cache through a mistyped string.
Server functionsinvokeAI · autoScheduleTasks · getUserCalendarEvents · importCalendarEvents · syncTasksToCalendar · registerPushToken · sendPushNotification · sendSupportEmail · deleteAccount · reconcileEntitlement · dailyPrioritiesWidget
AI gatingPaid capability is enforced on the server — invokeAI reads the stored plan and refuses paid features. The app's checks are for presentation only, so the rule cannot be bypassed from the device.
Offline readsThe task cache is written to device storage on every change and restored before the first frame: versioned, expiring after 24 hours, and erased on sign-out.
Failure behaviourIndependent data sources settle separately, so one unavailable source degrades its own section rather than blanking the screen.

5Authentication

Two ways in, sharing one session.

EmailDirect API sign-in and registration, with one-time-code verification and password reset. No browser involved.
Google / AppleRuns in ASWebAuthenticationSession, Apple's secure system browser. This is required, not preferred: Google refuses to complete sign-in inside an embedded web view. Because the backend cannot redirect to a private URL scheme, it returns to a page on its own domain which hands the session back to the app as capri://auth.
StorageThe session token is held in the iOS Keychain, in a shared access group so the widget can read it without a second copy existing anywhere on disk.
Session lifeRenewed silently before expiry. A rejected session clears the in-memory cache, the saved offline cache and the widget's data together, so no trace of one account survives into the next.

6Subscriptions — RevenueCat

SDKreact-native-purchases 10.7, configured with the publishable iOS key.
Entitlementcapri_executive, sold as capri_executive_monthly and capri_executive_annual.
ContinuityThe same RevenueCat project, key and entitlement as the previous app — an existing subscriber is recognised immediately and is never asked to buy again.
Pricing displayPrices are read live from the App Store and shown on the buttons in the user's own currency, rather than being discovered only at the payment sheet.
Source of truthThe server decides. A RevenueCat webhook writes the plan onto the user record; at each sign-in reconcileEntitlement re-checks and repairs the plan if a webhook was ever missed.
Failure behaviourA cancelled purchase does nothing. An unavailable store, a missing product or a network failure each produce a plain sentence for the buyer — no technical text reaches the screen.
AndroidNo Google Play key exists, so purchasing reports itself unavailable rather than failing with an opaque SDK error.

7Push notifications

Notifications are sent by the server straight to Apple. There is no third-party delivery service in the path.

TransportApple Push Notification service over HTTP/2, authenticated with a signed token (ES256) generated and cached by the backend. Firebase is present in the app for one purpose only — asking iOS for the device's address — and never carries a message.
Device registryA PushDevice record per device: owner, platform, provider, address, environment and enabled state. This replaced a single field on the user record, which silently discarded every token and allowed only one device per person.
EnvironmentsEach device records whether it is a development or production build, so Apple's two separate address spaces are handled per device rather than by one global switch that is always wrong for half the fleet.
RemindersA scheduled sweep sends 30 minutes and 10 minutes before a start time, once each, silently during the user's quiet hours, evaluated in their own timezone.
Silent updatesA second, invisible message type wakes the app briefly to refresh the home-screen widget. Held for up to fifteen minutes and compared against a fingerprint of the last send, so an afternoon of edits produces one message rather than thirty.
HousekeepingApple reporting a device as gone disables that record automatically; temporary failures are retried with a backoff. Extending to Android is a second provider in the router — nothing that sends a notification would change.

8Native modules

Three small Swift components were written for capabilities React Native does not provide, each exposed through a thin Objective-C bridge.

CapriAppGroupReads and writes the storage area shared between the app and its widget, and asks iOS to redraw the widget.
CapriDeepLinkHolds the destination from a tapped notification until the app has finished starting, then hands it over — which is what makes a tap work from a cold launch rather than only when the app is already running.
CapriStartupRecords the moment of launch and reports how long the app took to become usable, so startup performance can be measured rather than estimated.
App delegateOwns the notification delegate directly, forwarding to any previously installed handler. This is necessary because messages sent straight to Apple carry none of the markers a third-party SDK looks for, so its callbacks cannot be relied upon.

9Widget architecture

ExtensionA WidgetKit extension, CapriWidgetExtension, offering the Daily Priorities widget in small and medium sizes.
Data pathThe app writes a compact snapshot of the current priorities into shared storage whenever they change. The widget reads that directly, so it draws instantly, works with no signal, and always agrees with the app about what to start.
FallbackIf no snapshot exists — a freshly installed widget — it fetches from the backend using the shared Keychain session, rather than keeping its own copy of the user's credentials.
Refresh policyA single owner triggers each redraw, so one change costs one refresh rather than two. iOS limits how often a widget may update, so this directly determines how current it stays across a day. A half-hourly timeline covers ordinary use; server-sent silent updates cover the app being closed.
Deep linksThe widget as a whole, and each row on the medium size, opens the specific task it names.
